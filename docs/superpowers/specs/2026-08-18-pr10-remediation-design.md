# PR #10 连接一致性修复设计

## 背景

PR #10 把逻辑连接扩展为按账号生成运行时连接，并新增命令、Web 面板与 Guoba 等管理入口。审查确认：各入口没有共享完整的候选配置校验，运行时生命周期仍依赖会随配置序号变化的显示名，兼容连接与新自动连接也可能同时占用同一事件来源。此外，QQBot 把多组消息的“部分成功”误当作整条完成，配置迁移和平台映射还有若干兼容缺口。

这些问题不能靠继续给每个入口增加局部判断解决。需要把“配置会产生哪些运行时连接”与“当前客户端应如何变成该计划”分别收敛为唯一入口，再让所有写配置的路径使用同一套验证和协调流程。

## 目标

1. 任意配置变化都先针对完整候选连接集完成 URL、账号、运行时名称和路由冲突校验，失败时不写盘、不改变运行时。
2. 配置写盘成功后，运行时客户端与完整新计划一致；不存在残留客户端、重复事件上传、错误账号继续上报或因序号变化无法停止的问题。
3. 自动根端点始终按有效账号展开；旧共享 `/ws/Yunzai` 路径与账号级自动连接不能同时为同一账号上传事件。
4. 老配置中的 `client.ws_connections`、连接级 `bot_id` 和自动路径在启动迁移后保持原有意图，且迁移幂等。
5. 命令、Web 面板、Guoba、配置 watcher 和直接 YAML 修改采用相同的有效配置规则。
6. QQBot 只有在能证明整条消息所有分组均已完成时才确认成功；部分失败不能计数为完整成功或返回完整撤回回执。
7. 每个已确认问题都有一条本地可复跑的回归测试。`test/` 继续不入库，测试由维护者在推送前本地跑；CI 的关卡是 typecheck、lint、build 与产物冒烟。
8. README、帮助、默认配置与实际连接模型一致，不再文档化 `bind=all`。

## 非目标

- 不修改 gsuid_core、QQBot-Plugin 或 Yunzai 框架源码。
- 不改变现有配置文件的总体 YAML 结构。
- 不增加新的数据库或网络依赖。
- 不把每次配置变化都实现为无条件重启全部客户端；只停止、启动或替换与新计划不一致的客户端。
- 不在本次修复中处理 PR 基线已存在且未被本 PR 放大的媒体流内存上限问题。

## 方案比较

### 方案 A：统一计划与协调（采用）

保留 `expandConnections()` 作为完整配置到运行时计划的纯函数，在其输出中加入稳定的运行时身份。所有管理入口先构造完整候选连接数组，调用统一验证器；写盘后调用统一协调器使 `clients` 与最新计划一致。

优点是规则只有一个真源，能够覆盖命令、Web、Guoba、watcher 和手改 YAML；运行时更新可按差异执行，不会无条件中断无关连接。代价是需要调整配置写入 API 和生命周期调用点。

### 方案 B：逐入口修补（不采用）

分别给新增、编辑、删除、绑定、开关与 Guoba 保存补校验和重启。改动较分散，并继续允许入口之间产生不同语义，无法可靠覆盖 watcher 和手改 YAML。

### 方案 C：配置变化后全量重启（不采用）

每次变化直接清空全部客户端并重新展开。实现简单，但修改单个账号也会中断所有核心连接，不符合运行要求。

## 连接计划

### 稳定身份

`RuntimeWsConnection` 增加稳定的 `runtimeKey`。它由规范化后的运行时路由生成：协议和主机使用 URL 解析后的规范形式，路径保留大小写，查询参数不参与路由身份。自动连接的账号已编码在路径中；兼容连接的自定义路径直接构成身份。

显示名称 `runtimeName` 只用于日志和界面，不再作为客户端停止、复用、计数归属或冲突仲裁的唯一键。未命名连接因删除前项而从“连接 #2”变为“连接 #1”时，`runtimeKey` 不变，协调器更新显示元数据而不会遗留旧客户端。

同一路由在完整计划中只能有一个所有者。路径大小写不同的路由保持独立；协议和主机大小写差异视为同一路由。

### 自动端点与兼容端点

根端点必须至少有一个有效账号，并为每个账号生成 `/ws/Yunzai-<账号>` 运行时连接。自定义路径只生成一条兼容连接。

旧共享 `/ws/Yunzai` 连接如果与账号级自动连接覆盖相同账号，不能继续作为并行事件上传通道。迁移优先把可确定账号的旧自动路径还原为根端点加 `bind`；无法确定账号的共享兼容连接保留但进入全局覆盖检查，要求用户显式绑定、排除或停用，不能静默双传。

`bind: []` 不再表示任意账号。自动端点的空绑定是无效配置；兼容端点的空绑定只用于无法安全推断账号的旧配置，不参与“任意账号”重复判定，也不能阻止用户首次绑定明确账号。

### 完整候选校验

新增纯校验入口，输入完整候选 `WsConnection[]`，输出运行时计划、警告和阻塞错误。阻塞条件包括：

- URL 无效或不是 `ws:` / `wss:`；
- 自动端点没有有效账号；
- 两条启用连接声明同一 `runtimeKey`；
- 多个来源会为同一账号上传同一事件；
- 运行时显示名或稳定键产生无法区分的冲突；
- 某次编辑、新增、绑定或开关导致请求目标未进入最终运行时计划。

同一账号同时出现在 `bind` 与 `exclude` 时继续沿用“`exclude` 优先”并返回警告。共享兼容连接等可以继续运行但需要迁移的状态也作为警告返回；会造成重复上传、账号被跳过或用户请求未生效的状态必须阻止写盘。

## 配置事务与入口

配置层提供候选更新 API：先从当前有效配置复制连接集，在内存中应用新增、修改、删除、绑定或整表替换，再运行完整候选校验。只有校验成功后才在一次 `saveConfig()` 中写入连接和关联的 `bot_id_map`，随后重载配置并协调运行时。

命令、Web 面板和 Guoba 不再各自决定路由是否有效，只负责把输入转换为候选修改及各自的错误响应格式。配置 watcher 读取外部变更后同样运行迁移和完整规划；若新文件无效，则保留当前生效配置和客户端，并记录明确错误，不能合并默认示例后连接到错误地址。

编辑 URL 时使用结构化 URL API：保留原 URL 中所有非 `token` 查询参数；用户提交的新 URL 显式包含某参数时以新值为准。`token` 继续迁移到专用字段并保持脱敏。

### 平台映射

连接级旧 `bot_id` 在迁移时按该连接的每个有效 `bind` 写入 `bot_id_map`，已有账号级显式值优先；完成后移除连接级字段。无法关联账号的旧 `bot_id` 保留并给出迁移警告，不能静默丢弃。

新增、合并或编辑时，用户显式输入的 `id=` / `bot_id` 对本次明确选择的账号使用 `force=true` 覆盖旧映射。自动推断只补空值，不覆盖用户记录。成功回显必须从写盘后的实际 `config.bot_id_map` 读取，不能直接复述输入值。

`resolveBotId()` 先判断 QQBot 频道事件，再使用普通 QQBot 账号映射，确保 `qg_*` / guild 事件得到 `QQGuild` 对应的 `qqguild`。频道特判高于账号级普通映射：同一个 QQBot 账号的群事件可以使用账号映射 `qqgroup`，频道事件不能被该映射覆盖。

## 运行时协调

新增 `reconcileClients(plan)`，以 `runtimeKey` 比较当前客户端和目标计划：

1. 目标中不存在的客户端先关闭并移除。
2. 路由相同但**握手时读取**的字段改变时替换客户端：运行时地址（含非 `token` 查询参数）、`token`、地址是否内联携带 token。这三项在 `connect()` 建连那一刻读一次，原地换配置只会让下一次重连用上新值，而正在跑的那条仍带着旧凭据，核心侧可能已经拒了它，两边状态不一致且没有任何提示。
3. 行为未变时原地更新元数据与配置引用，不断线：既包括来源序号与显示名称，也包括**每次使用时现读**的字段 —— `bind` / `exclude`（`accept()` 逐条消息读）、`reconnect_interval` / `max_reconnect_attempts`（每次退避现读）。换掉配置引用它们就生效，为它们重连是白丢消息（退避 5 秒起步，期间上下行真的没了）。
4. 目标中新增的客户端最后启动。
5. 适配器或 WS 总开关关闭时目标计划为空，所有客户端停止。

先停后起不能反：被停的那条可能正占着新那条要用的路由（改地址、账号换大小写写法）。先起会撞上同路由去重而静默失败，随后旧那条才被停掉 —— 结果两条都没了。

所有配置变更入口统一调用协调器。按来源精确停起的那套旧 API（`stopSource()`、`startSource()`、`shiftSourceIndex()`、按显示名的 `stopClient()`）直接删除而非保留不用：它们全都建立在「一次改动只影响被改的那一条」这个不成立的前提上，留在导出面上迟早会有新入口照着用。手动重连能力由客户端自身的 `restart()` 承担，与状态收敛无关。

协调在写盘后发生；若创建新客户端同步失败，记录错误并保证旧配置对应客户端已经正确停止，不允许继续携带已解绑账号运行。Web 和状态页均按稳定键/来源元数据聚合，不再按显示名猜测客户端归属。

## QQBot 投递语义

QQBot 返回的 `data.length > 0` 只表示至少一个分组成功，不能表示整条完成。适配器侧定义投递分类：

- `complete`：返回值明确没有当前失败，或能证明所有最终分组成功；
- `partial`：同时存在成功数据和最终失败；
- `failed`：没有任何成功且存在失败；
- `unknown`：返回形状不足以证明结果。

只有 `complete` 才计入完整下行成功并返回正常撤回 ID。`partial` 记录错误并只返回已成功分组的撤回 ID，但不能把整条计为成功；如果上游没有提供可精确重试的失败分组，不进行整条自动重发，以免复制已经成功的内容。`failed` 沿用普通发送回退；`unknown` 使用保守的既有 `sendError()` 语义。

被动发送路径与普通发送后的统计、日志、回执共用同一个分类函数，避免一处认为成功、另一处认为失败。

## 测试设计

先新增失败测试，再修改实现。至少覆盖：

1. 删除第一条未命名连接后，后续客户端的稳定键不变、显示名更新，解绑能真正停止客户端。
2. 编辑、删除、绑定和开关会重新计算全局仲裁；被前项释放或新冲突占用的路由正确启停。
3. 默认空 `bind` 不阻止首次账号绑定，也不作为所有账号通配符。
4. 旧共享连接与新账号自动连接不会同时上传同一账号事件。
5. 旧自动路径合并多个账号时生成逐账号运行时连接，不保留 `account:null` 共享客户端。
6. 某个新增账号被规划器跳过时，新增、合并和编辑均拒绝写盘。
7. Guoba 整表保存执行与命令/Web 相同的 URL、账号和路由校验。
8. 修改 URL 保留 `tenant`、`access_token` 等非 `token` 查询参数。
9. `BotA` 与 `bota` 生成大小写不同的路径并同时启动；主机大小写差异仍冲突。
10. 旧连接级 `bot_id` 按账号迁移且二次启动不重复改写。
11. QQBot 频道事件优先解析为 `qqguild`，普通群仍为 `qqgroup`。
12. 新增、合并和编辑中的显式 `id=` 均覆盖旧账号映射，自动推断不覆盖。
13. QQBot 完全成功、首轮失败后最终成功、部分最终失败、完全失败和未知返回形状分别得到正确分类、统计、回退与回执。
14. watcher 收到旧格式配置时先迁移；收到无效配置时保留当前运行状态。
15. 已有 190 个测试与新增测试在一次本地 `pnpm build && pnpm test` 中全部通过。

测试留在本地：`test/` 仍在 `.gitignore` 里，CI 克隆不到，因此构建与发布工作流不加 `pnpm test` 步骤，关卡仍是 `pnpm typecheck`、`pnpm lint`、`pnpm build` 与锅巴入口冒烟加产物完整性自检。测试由维护者在推送前跑一遍，红着不推 main。

本地跑法是 `pnpm build && pnpm test`，顺序不能颠倒。测试本身不读 `lib/`——它们用 `await import("../src/**.ts")` 让 `tsx` 现场转译源码（见 `test/fixtures.mjs` 的说明），但 `classes.test.mjs` 会断言 Tailwind 产物 `resources/template/css/tailwind.css` 真的被内联进了 CSS，那份产物由 `pnpm build` 的 `build:css` 步骤生成，缺了它这条测试就红。

## 文档与兼容性

README、帮助页、配置指南和默认配置统一说明：

- 根端点需要明确 `bind`，一个账号一条运行时 WebSocket；
- `bind=all` 不再支持；
- 自定义路径是兼容模式，不会自动按账号派生；
- `bot_id_map` 按账号保存平台标识；
- 旧配置会迁移，无法安全推断的共享连接需要用户确认。

修正 `docs/guide/panel.md` 的 EOF 空行，保证 `git diff --check` 通过。

## 验收标准

- 所有已确认的 PR 审查问题都有至少一个可复现的回归测试，或属于纯文档/格式项并由对应检查覆盖。
- 任意管理入口保存后，`clients` 与完整 `expandConnections(getWsConnections())` 计划一致。
- 配置中已解绑、删除或被冲突淘汰的账号不存在仍在运行的客户端。
- 同一账号事件不会因兼容连接和自动连接并存而上传两次。
- QQBot 部分失败不会被记录为完整成功，也不会静默确认整条投递完成。
- `pnpm typecheck`、`pnpm lint`、`pnpm build`、`pnpm test`、`pnpm docs:build` 和 `git diff --check main...HEAD` 在本地全部通过（`pnpm test` 依赖 `pnpm build` 产出的 Tailwind 产物，两者顺序不能颠倒）。
- PR 复审无 P1/P2 阻塞项后才允许合并；合并成功后删除远端 `fix/exact-multi-bot-resolution` 分支，并确认 PR 状态为 `MERGED`。
