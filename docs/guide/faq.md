# 常见问题

按现象找。每一条都给到下一步该做什么 —— 日志里的那句话通常已经指明是哪一环出了问题。

## 连不上，日志刷「连接错误」

按顺序过一遍：

1. **核心真的在跑吗** —— 看核心自己的日志，或在浏览器里访问一下它的地址
2. **地址端口对不对** —— 发 `#早柚连接列表`，看插件手里存的是哪个地址
3. **token** —— 核心那边配了鉴权的话，`token` 要一致
4. **地址只写到 `host:port`** —— 不要带 `/ws/Yunzai` 这类路径，那段由插件自己拼
5. **容器 / 异机部署** —— 地址别写成容器内部的 `127.0.0.1`，那指的是云崽自己

重连是有上限的：默认试 5 次、约覆盖 2.3 分钟，之后日志写「达到最大重连次数 N，停止重连（可用 `#早柚重连` 恢复）」就不再自己试了。核心晚一点才起来的话发 `#早柚重连`；想让它一直重连，把连接的 `max_reconnect_attempts` 改成 `0`。

## 连接卡片显示「未启动」

这类是**压根没启动**，不是连不上。原因就那几种，启动时就已经报了：

| 日志里那句话 | 怎么办 |
| :--- | :--- |
| 连接 X 缺少 url，已跳过 | 补上核心地址 |
| 连接 X 的 url 无法解析或不是 WebSocket 地址，已跳过 | 地址要写成 `ws://host:port`（`#早柚添加连接` 会替你补 `ws://`） |
| 连接 X 没有可用的绑定账号，已跳过 | `#早柚修改连接 <序号> bind+=<账号>`，或用[面板](./panel.md)的账号开关 |
| 连接路径冲突，已保留 A，跳过 B | 两条连接算出了同一条路径（多半是绑了同一个账号）。删掉多余那条，同一个核心只留一条连接、靠绑定账号挂多个号 |

在[面板](./panel.md)上，这些原因写在连接区顶上的红框「有连接没能启动」里。**状态图上不给原因**，只显示「未启动」—— 要看原因去日志或面板。

## 两个机器人号连同一个核心，一个连上另一个就掉

核心是按**路径**认客户端的，两个号共用一条路径就会互相顶掉。插件现在给每个绑定账号各生成一条 `/ws/Yunzai-<账号>`，本来不该出现这种事。检查两处：

- 配置里的 `url` 有没有被手写成 `/ws/Yunzai`（那会被当成[自定义路径](./config.md#多个账号接同一个核心)，只起一条 ws、多个号共享它）
- 两个号是不是各配了一条连接。同一个核心只留**一条**连接，把两个号都写进它的 `bind`：在另一个号上发一次 `#早柚添加连接 <同一个地址>` 即可

## 连上了，但核心那边没反应

1. **核心侧收到消息了吗** —— 看核心日志。没收到就是没上报，往下看第 3 条
2. **平台标识对不对** —— 核心用 `bot_id` 区分平台，认错了插件就不触发。发 `#早柚修改连接 1 id=qqgroup`（或在 `bot_id_map` 里给这个账号加一行）。`#早柚状态` 和面板上能看到每个号被认成了什么，显示「未识别」说明没推断出来
3. **这个号真的绑在这条连接上吗** —— `#早柚连接列表` 里绑定账号显示为头像胶囊，面板上展开账号区能逐个看。同时写进 `bind` 和 `exclude` 的号不会转发（`exclude` 优先），面板会在那一行标红
4. **是不是被过滤挡了** —— `filter.only_reply_at` 开着时群里必须 @ 或带前缀；`block_prefix` / `block_include` / `white_group` / `black_group` / `black_user` 也都会拦。见[配置](./config.md#谁的消息进核心)

## 每条消息被处理两次，核心回两遍

同一条消息被两套适配器上报了。插件启动时会自己查，日志里已经写明是哪一个：

- **别的插件也配了核心连接** —— 日志：「检测到 `<目录>` 也配了早柚核心连接（type: 3）」。多见于 ws-plugin。二选一：在那个插件里删掉这些连接（或把 `enable` 设为 false），或者把本插件的 `enable` 关掉
- **框架自带的 `plugins/adapter/GSUIDCore.js`** —— 日志会建议删掉它。它面向旧版核心（等核心来连云崽），与现在的核心行为已经不一致

还有一种是自己配了两条连接覆盖同一个账号，这种在保存时就会被拦下来并告诉你撞上了谁。

## 图片发不出去 / 核心拿到占位图

超过 `media_max_size` 的图要走 http 外链，问题基本都在「核心拉不到这个链接」：

- **TRSS-Yunzai** 用框架自带的文件服务生成外链，地址由框架自己的配置决定（`server.url`）。核心在 Docker 里而它给的是 `127.0.0.1` 就拉不到 —— 把它配成核心可达的地址
- **Miao-Yunzai** 走插件内置的文件服务，正常会自动取 ws 连接的本机地址。跨网段 / 跨容器导致推断不对时，用 `file_server.public_host` 写死云崽的可达地址，并确认 `file_server.host` 不是 `127.0.0.1`
- 日志里「内置文件服务挂载失败，尝试图床」多半是端口被占，把 `file_server.port` 改回 `0` 交给系统分配
- 日志里「当前框架不提供 `Bot.fileToUrl`……」说明框架没有文件服务，而内置的那个也没起来 —— 按上一条查，或配一个 `upload_hook` 图床

实在不想折腾就调大 `media_max_size` 让图片走 base64 内联（上限 256 MB，代价是内存）。

**大文件另说**：`file` 段在协议里只能内联，没有外链兜底。日志写「file 段 X.X MB 超过上限 Y.Y MB，已跳过」就只能调大 `file_max_size`。三项的单位与上限见[配置](./config.md#大小与有效期这三项)。

## QQ 官方机器人上本该出图，却什么都没收到

核心给官方机器人发「图片 + 按钮」时会把图文压成一段 markdown，而那一步要求核心自己先把图片转成外链。核心的「图片发送方式」选了链接却没配图床时，转链接那步落空 —— 图片既没写进 markdown 也没留在消息里，被核心丢掉了，纯图片的响应（比如某些插件的帮助图）到适配器手上就只剩一个空 markdown 加一组按钮。

日志里的那句话：`核心下发了空 markdown，已跳过；若本该是图片，检查核心「图片发送方式」与图床配置`。

**这是核心侧的配置问题，适配器补不回那张图**（它压根没离开核心）。两条出路：改核心的图片发送方式，或者按[让核心的图走本机图床](./config.md#让核心的图走本机图床)把转接口挂上。

## 按钮 / markdown 发出去没了

不是每个适配器都发得出这两种消息段，而核心不知道下游是什么平台、一律照发。Milky / OneBotv11 没有 button / markdown 分支，OPQBot 连 `video` / `file` / `reply` 都直接跳过。

本插件**不做降级** —— 再加一层「转成文本」只是用噪音替换静默丢弃，内容并没有真的送达。按钮目前基本只有 QQ 官方机器人在用，而它原生支持。要按钮就用支持按钮的适配器。

日志里「暂不支持的消息段类型 X，已跳过」也是同一类：那个段本插件还没做映射。合并转发是个例外，做不出来时会降级成普通消息，日志写「转发消息制作失败，已降级为普通消息」。

## 撤回不管用了

核心那边拿不到消息 id 就会停用撤回能力。适配器这侧只要收到带回执要求的下发就一定回一帧回执，哪怕当时取不到 id（那就回一个空的），所以问题一般不在这儿。

- 检查当前适配器的 `sendMsg` 返回值里有没有 `message_id` —— 取不到就没法撤回
- 核心那个「不支持撤回」的判断只活在它自己的进程里，**重启核心**
- 日志写「当前适配器不支持撤回消息」是另一回事：核心让适配器去撤回，而这个适配器没有撤回接口

## 主人老被断线通知刷屏

`notify_master` 默认是关的，开了才会在断开与恢复时私聊主人。核心常重启的话把它关掉：`#早柚设置断线通知关闭`。

`#早柚重连` 和手动停用不会触发通知。

## 改了配置好像没生效

三个入口改完都即时生效，不用重启云崽。还是不对的话：

- 手改 `config/config.yaml` 后日志里报「配置重载校验失败」—— 那份改动没有被采用，插件仍按旧配置在跑。报错里写了是哪条连接的什么问题
- 心跳那两项改了会自动重连一次，这是正常的
- 核心的 `pic_upload_config.json` 那几项是例外，改完**必须重启核心**，热重载不管用
